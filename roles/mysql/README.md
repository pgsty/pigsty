# Role: mysql

> Deploy native MySQL 8.4 standalone or three-node InnoDB Cluster

| **Module**   | MYSQL (PILOT)                                                           |
|--------------|-------------------------------------------------------------------------|
| **Playbook** | `mysql.yml`                                                             |
| **Removal**  | `mysql-rm.yml`, `mysql_remove`                                          |
| **Example**  | `conf/demo/mysql.yml`                                                   |
| **Stack**    | MySQL 8.4, Group Replication, MySQL Router, XtraBackup, mysqld_exporter |

Sandbox validation: [实机测试记录](TESTING.zh-CN.md).


## Overview

The role manages one MySQL instance per node and accepts exactly two topology
shapes:

- one member: standalone MySQL;
- three members: InnoDB Cluster using single-primary Group Replication.

MySQL is a fixed Pigsty platform, not a general MySQL installer. The server,
client, Shell, Router, and XtraBackup line is fixed at 8.4. Public variables do
not expose package versions, ports, character set, TLS paths, memory sizes, or
timer expressions. The data and backup directories are the only public paths.

In HA mode, MySQL Shell AdminAPI forms and reconciles the cluster. `mysql_seq=1`
is only the initial coordinator; the runtime PRIMARY is discovered and is not
forced back to sequence 1 on reruns. Every member runs Router with classic RW
and RO endpoints on `6446` and `6447`.

MYSQL remains a PILOT module. Ordinary reconciliation refuses unknown datadirs,
foreign InnoDB Cluster metadata, partial HA inventory limits outside the
provision, backup, and monitor phases, and destructive Clone over non-fresh
members.

`mysql.yml` targets `all` for inventory convenience but ends each host without
`mysql_cluster` before role execution. Hosts selected as MySQL members must
define both `mysql_cluster` and `mysql_seq`; the role then validates complete
one-member or three-member cluster scope before changing state.

The native package gate admits the declared x86_64 DEB/RPM matrix and EL9/EL10
ARM64. Ubuntu/Debian ARM64 is intentionally rejected because Oracle's APT
repository currently publishes the 8.4 component for `amd64`, not `arm64`.


## Public Interface

Only the following variables are intended for inventory use:

| Variable                 | Default          | Description                           |
|--------------------------|------------------|---------------------------------------|
| `mysql_cluster`          | required         | cluster name; normally group name     |
| `mysql_seq`              | required         | `1` for standalone, `1..3` for HA     |
| `mysql_root_password`    | `DBUser.Root`    | local root password                   |
| `mysql_monitor_password` | `DBUser.Monitor` | exporter account password             |
| `mysql_cluster_password` | `DBUser.Cluster` | AdminAPI and backup password          |
| `mysql_databases`        | `[]`             | additive database declarations        |
| `mysql_users`            | `[]`             | additive user and grant declarations  |
| `mysql_parameters`       | `{}`             | extra `[mysqld]` overrides, last wins |
| `mysql_data`             | `/data/mysql`    | data directory, with binlog and tmp   |
| `mysql_backup_enabled`   | `true`           | enable one daily full backup timer    |
| `mysql_backup_dir`       | `/data/backups/mysql` | local backup directory           |
| `mysql_backup_retention` | `3`              | full backups to keep                  |
| `mysql_exporter_enabled` | `true`           | exporter service and target state     |

The fixed defaults live in [`vars/main.yml`](vars/main.yml) and are internal.
The monitoring password must not contain INI interpolation such as `%(host)s`;
the exporter would substitute these expressions instead of using the literal password.
The InnoDB buffer pool takes half of `node_mem_mb`, or a quarter on a node
shared with PostgreSQL; redo capacity follows it and replica workers follow
`node_cpu`. `max_connections` defaults to 1000. Inventory host names are the
advertised MySQL and MGR addresses, matching the rest of Pigsty's node model.

`server_id` is the IPv4 service address as an integer, so it stays unique
across clusters that replicate with each other. The Group Replication UUID is
generated by AdminAPI and owned by the cluster.

`mysql_data` used to be fixed at `/var/lib/mysql`. A node that already holds
an initialized datadir there must keep `mysql_data: /var/lib/mysql`; the role
refuses to start an empty datadir next to it. On Debian and Ubuntu the role
adds the directory to the local AppArmor profile. Pigsty nodes run SELinux in
permissive mode; an enforcing node needs the default path or its own labels.

Example:

```yaml
my-test:
  hosts:
    10.10.10.11: { mysql_seq: 1 }
    10.10.10.12: { mysql_seq: 2 }
    10.10.10.13: { mysql_seq: 3 }
  vars:
    mysql_cluster: my-test
    mysql_databases:
      - { name: app }
    mysql_users:
      - name: app
        password: DBUser.App
        priv: { 'app.*': 'ALL PRIVILEGES' }
```


## Components

| Component         | Purpose                                        | Endpoint                   |
|-------------------|------------------------------------------------|----------------------------|
| `mysqld`          | standalone server or MGR member                | `3306`, X Protocol `33060` |
| Group Replication | three-member consensus and replication         | `33061`                    |
| MySQL Router      | topology-aware client routing on every HA node | RW `6446`, RO `6447`       |
| MySQL Shell       | AdminAPI cluster lifecycle                     | local control plane        |
| XtraBackup        | one daily prepared full physical backup        | local storage              |
| mysqld_exporter   | server and MGR metrics                         | `9104`                     |

The role creates three platform identities:

- `dbuser_cluster@'%'`: TLS-only AdminAPI account;
- `dbuser_monitor@'127.0.0.1'`: least-privilege exporter account;
- `dbuser_backup@'localhost'`: local XtraBackup account.

Declared databases and users are additive. The role does not implicitly drop
objects or revoke grants.

Every member gets two shortcuts in `/etc/profile.d/mysql.sh`: `my` opens the
local root client, and `mysh` runs AdminAPI code as `dbuser_cluster`, printing
the cluster status by default:

```bash
my -e 'SHOW PROCESSLIST'
mysh                                                           # cluster status
mysh 'dba.getCluster().setPrimaryInstance("10.10.10.12:3306")' # switchover
```


## Access

Every HA member runs a Router, so any member address works. For one stable
entry, enable the node VIP on the MySQL node cluster (`vip_enabled`,
`vip_address`, `vip_vrid`): keepalived floats it across the members, clients
connect to `<vip>:6446` and `<vip>:6447`, and the role adds the VIP to the
certificate.


## PKI

`node_ca` owns the trusted node CA and installs it once at
`/etc/pki/ca.crt`. The MySQL role requires that prerequisite and never copies
the CA into MySQL, Router, or Exporter directories.

The controller-side CA is used only to sign the MySQL leaf certificate:

```text
files/pki/
├── ca/ca.crt
├── ca/ca.key
├── csr/<instance>.csr
└── mysql/<instance>.{key,crt}
```

Each node gets one certificate containing its address, instance name, cluster
name, and localhost SANs. Mysqld and Router share that same leaf certificate;
the private key is readable only by their service identities. All clients and
services reference the shared `/etc/pki/ca.crt` trust anchor.


## Monitoring

Each node has one VictoriaMetrics file-SD document:

```text
/infra/targets/mysql/<instance>.yml
```

The document contains only the mysqld_exporter target. Vector journal
registration remains in the existing per-node Pigsty configuration. Ordinary
reconciliation overwrites this document, using `[]` when the exporter is not
enabled; only `mysql_remove` deletes target files.

The alert set is small on purpose; diagnostic signals stay on the dashboards:

| Alert                   | Level | Meaning                                      |
|-------------------------|-------|----------------------------------------------|
| `MySQLDown`             | CRIT  | exporter cannot connect to mysqld            |
| `MySQLClusterDown`      | CRIT  | quorum lost, or not exactly one primary      |
| `MySQLExporterDown`     | WARN  | exporter is not scraped                      |
| `MySQLClusterDegraded`  | WARN  | a member is not ONLINE                       |
| `MySQLReplicationLag`   | WARN  | a Group Replication queue stays above 1000   |
| `MySQLConnUsageHigh`    | WARN  | above 80% of `max_connections`               |
| `MySQLHistoryListLarge` | WARN  | a long transaction blocks purge              |
| `MySQLBackupStale`      | WARN  | no successful backup in the cluster for 30h  |


## Backup

The v1 backup contract is deliberately small:

- fixed daily systemd timer, plus an initial backup if no committed backup exists;
- full physical XtraBackup only, prepared and uncompressed;
- backup runs on standalone or the current MGR PRIMARY;
- `mysql_backup_dir` holds the last `mysql_backup_retention` backups, each as
  large as the data.

A successful backup writes `mysql_backup_last_success_timestamp_seconds` and
`mysql_backup_size_bytes` through the node_exporter textfile collector, which
feeds the `MySQLBackupStale` alert. A failed first backup writes a zero timestamp
so it also alerts; later failures preserve the last success. Rerunning
`mysql.yml` retries an initial backup that failed.

There is no public schedule expression, incremental chain, continuous binlog
archive, or restore automation. Physical restore is a separate, destructive
operator runbook rather than an executable installed by this role.

## Safety and Operation

The normal role never clears a datadir or forces a cluster operation. A
non-empty datadir must carry Pigsty's exact cluster/instance/topology marker.
In HA mode, ordinary reconciliation also refuses an implicit
`mysql_cluster_password` rotation; password rotation requires a dedicated
operator procedure.

Two recoveries run inside ordinary reconciliation, because they need no
judgement once every declared member is reachable:

- **Lost member**: bring up a fresh machine at the same address and run
  `mysql.yml`. The stale registration is dropped and the member is cloned
  back. Changing a member address is not supported.
- **Complete outage**: start every member and run `mysql.yml`. AdminAPI
  reseeds the group from the most advanced member without force. With a member
  unreachable the role stops and leaves that decision to the operator.

Users and databases do not need the whole cluster: `-t mysql_provision`,
`-t mysql_backup`, and `-t mysql_monitor` accept a partial limit, as long as
the runtime PRIMARY is inside it for provisioning.

Removal lives in `mysql_remove` and follows the other Pigsty modules:
`mysql_safeguard`, `mysql_rm_data`, and `mysql_rm_pkg`.

Before a real run, inspect the selected nodes and backups, then preview the
complete cluster scope:

```bash
./mysql.yml -l my-test --check
./mysql.yml -l my-test                 # requires explicit change approval
```

Syntax-only validation does not touch target nodes:

```bash
ansible-playbook -i conf/demo/mysql.yml mysql.yml --syntax-check
ansible-playbook -i conf/demo/mysql.yml mysql-rm.yml --syntax-check
```
